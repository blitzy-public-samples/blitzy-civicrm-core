# STORY-004 — Recurring-gift receipt download

The fourth and final story of the Epic defined in [`epics.md`](epics.md), which also carries the
story roster, the JIRA import reconciliation and the consolidated clarification summary. This
document carries the nine mandated story fields and nothing else — there is no Epic field among
them, by design.

This story adds **one verb** to a contract it does not own. Ownership, scoping and eligibility are
enforced exactly as
[`STORY-003-recurring-gift-receipt-viewing.md`](STORY-003-recurring-gift-receipt-viewing.md)
defines them, and the scoping predicates are the four published once in
[`STORY-001-donor-identity-and-self-only-scoping.md`](STORY-001-donor-identity-and-self-only-scoping.md);
where a predicate appears below it is referred to **by its number in that contract** and is never
redefined here. STORY-003 is consequently the **sole direct predecessor** — STORY-001 and STORY-002
are reached transitively through it, which is why the Dependencies field names STORY-003 alone.

What this story adds is **file delivery**, and nothing else. It is the only story in the Epic at
Priority Medium for exactly that reason: it introduces no record-level boundary of its own. The
roster and the reasoning behind that priority are in [`epics.md`](epics.md) §4.3.

## Story ID

STORY-004

---

## Title

Recurring-gift receipt download

---

## Description

Deliver the same receipt content as a downloadable file a donor can keep, under **identical**
ownership, scoping and eligibility enforcement to the viewing path, and reached by the same
row-level link mechanism with the display's `actions` setting left false.

**"Identical" is the operative word, and it is a design instruction rather than a description.**
The download path re-applies the same four predicates against the same server-derived identity,
refuses under the same non-disclosing contract, and honours the same status-eligibility set as the
viewing path — by *referring* to that one contract rather than by carrying its own copy of it. A
download path holding a second copy of the rule is a path that can silently drift from the viewer
it is supposed to mirror, and the failure that produces is a donor obtaining as a file something
they are not permitted to see on screen.

**Where the delivered format is a PDF**, rendering runs through
`CRM_Utils_PDF_Utils::html2pdf()`, whose engine is chosen by configuration — WeasyPrint, then
wkhtmltopdf, then bundled dompdf. So this story carries the **host prerequisite** that the first
two imply: their PHP wrappers are present in the dependency lock, while the external executables
they drive are not guaranteed to exist on the target instance. That is a provisioning question,
not a dependency question, and the story states it as such.

---

## Business Value

Gives a donor their own copy to keep — for personal and tax records — without asking staff to send
one.

The business objective supplied with this request records that **a donor who wants a copy of a past
receipt has to ask staff for it**, and that **donors are frustrated at being unable to do simple
things themselves outside business hours**, because the queue only moves while the office is open.
A download request is the clearest instance of both: the donor knows exactly which record they
want, and producing the file needs no judgement that a person has to supply — yet today the request
joins the queue that **costs the team several hours a week** across the people who field it.

It completes the **download** half of the success criterion that a donor can *view and download a
receipt for any past contribution generated by their recurring gift(s) specifically*; STORY-003
delivers the view half, against the same contract. It also delivers the criterion that the
self-service area is reachable **without calling or emailing staff** — a criterion that is not met
while the only route to a file a donor can keep still runs through a staff member.

The priority is **Medium**, and the reason belongs here rather than being left to inference: this
story introduces no new record-level boundary, inheriting STORY-003's whole. The criterion that the
portal exposes only a donor's own history, never another donor's, is delivered by STORY-001,
STORY-002 and STORY-003 — which is why those three carry High and this one does not
([`epics.md`](epics.md) §4.3).

## Acceptance Criteria

[ ] Given a donor viewing a receipt they own, when they request a download, then a file is returned whose content corresponds to the receipt displayed.

[ ] Given an identifier the donor does not own, or one failing any scoping or eligibility predicate, when a download is requested for it, then the same non-disclosing refusal contract that STORY-003 defines applies, verified against the identical case list — an identifier that does not exist, one the donor does not own, one whose recurring link is null, one flagged as test-mode, one dated in the future, and one outside the eligible-status set — with all six producing one identical response.

[ ] Given a contribution with no recorded `receipt_date`, when a download is requested, then the behaviour defined for the viewing path applies and no empty or malformed file is returned.

[ ] Given a download completes, then no column of the contribution record is written, and no new logging or audit capability is exercised beyond what `CLR-10` authorises for the chosen route.

[ ] Given the donor-facing display, when its configuration is reviewed, then `actions` remains false and the download affordance is a row-level link, so no bulk task and no result-set export is reachable by a donor role.

## Technical Notes

Every claim below is a **reading of source at the stated address**, obtained by static inspection
of this checkout. No runtime was stood up for this run — no CiviCRM instance was installed, no
request was issued, no file was rendered and no data was retrieved — so nothing here rests on
observed behaviour, and any statement about what a *particular deployment* has configured or
installed is raised as a clarification rather than asserted. The baseline is CiviCRM `6.17.alpha1`
([`xml/version.xml`:3]); a different target version must be re-checked against these addresses
before the story is estimated as it stands.

**Enforcement is the viewing path's, referenced and not restated.** All four of STORY-001's
predicates — 1 through 4, in the numbering that contract publishes — plus whichever status set
`CLR-13` fixes are applied by this path too, server-side, on an identifier the caller supplies and
cannot widen. The definitions live in STORY-001 and STORY-003 and are deliberately not reproduced
here: a single normative statement is what makes the two receipt paths verifiably the same, and
restating it would create exactly the second copy whose divergence criterion 2 exists to catch.

**The existing donor route is both the precedent and the warning.** That route,
`civicrm/contribute/invoice`, is documented in STORY-003 — its declaration, its access callback and
the ownership gap in that callback — and this story takes that account as given rather than
re-establishing it. It is the **precedent** because the route already delivers a file to a donor,
so file delivery on this data is not novel work. It is the **warning** because of *how* it delivers
one: `getPrintPDF`
([`CRM/Contribute/Form/Task/Invoice.php`:671-677], the call out at
[`CRM/Contribute/Form/Task/Invoice.php`:676]) reaches `printPDF`
([`CRM/Contribute/Form/Task/Invoice.php`:250]), which writes a **stored file** through `putFile`
([`CRM/Contribute/Form/Task/Invoice.php`:487], [`:501`], [`:514`], defined at [`:664`], where it
delegates to `CRM_Utils_Mail::appendPDF`) and records an **Activity** through `addActivities`
([`:619`], the `Activity.create` call itself at [`:649`]). A donor download on that route is
therefore not side-effect-free today.

**Whether those side effects are acceptable for a donor read is `CLR-10`, and `CLR-10` is owned by
STORY-003.** Criterion 4 defers to it rather than pre-empting it, which is precisely why that
criterion is worded "beyond what `CLR-10` authorises for the chosen route" instead of the flatter
and more tempting "no file is written". This story asserts only the narrower promise it can keep
regardless of how `CLR-10` is answered: that **no column of the contribution record is written**.
Deciding the route's persistence behaviour here — in the story that merely consumes the route —
would settle a question belonging to the story that chooses it.

**PDF rendering: the engine is a configuration choice.** Where the delivered format is a PDF,
rendering runs through `CRM_Utils_PDF_Utils::html2pdf()` ([`CRM/Utils/PDF/Utils.php`:36]), which
selects an engine in a fixed order — a configured WeasyPrint path first
([`CRM/Utils/PDF/Utils.php`:120]), then a configured wkhtmltopdf path
([`CRM/Utils/PDF/Utils.php`:123]), then bundled dompdf as the fallback
([`CRM/Utils/PDF/Utils.php`:127]). Configuration decides; the calling code does not.

**No dependency is added by this story.** All three engines are driven through Composer packages
already present in the lock — `dompdf/dompdf` `v3.1.4`, `pontedilana/php-weasyprint` `1.4.0` and
`knplabs/knp-snappy` `v1.7.1` ([`composer.lock`]) — and the renderer instantiates the latter two
directly ([`CRM/Utils/PDF/Utils.php`:182] for WeasyPrint, [`CRM/Utils/PDF/Utils.php`:204] for
wkhtmltopdf), each constructor taking the executable path from the very setting that selected it.

**What differs between the engines is a host prerequisite, not a dependency change.** dompdf
renders in-process. The other two shell out to an **external executable at the configured path**,
so on an instance configured for either, that binary must be installed and present at that path.
It is resolved by provisioning the host, never by adding a package — and conflating the two is the
error this note exists to prevent, because the wrappers being in the lock makes the capability
*look* self-contained when it is not.

`CLR-12` therefore has a testable hook rather than needing a manual trawl through settings: the
public helper `getPdfEngine()` ([`CRM/Utils/PDF/Utils.php`:131-141]) reports which of the three the
current configuration selects, by the same three-way test the renderer itself applies. Asking it
which engine is live, and then confirming that engine's binary is present, is the whole of the
target-instance half of that question.

**SearchKit's own download action is not the mechanism.** It streams a *result-set* export and
refuses outright any display whose `actions` setting is off, answering with `permissionDenied()`
([`ext/search_kit/Civi/Api4/Action/SearchDisplay/Download.php`:31-34]); the same gate guards file
save ([`ext/search_kit/Civi/Api4/Action/SearchDisplay/SaveFile.php`:65]). This story delivers **one
rendered receipt**, not a result set, so neither action is a candidate. Bulk or list-level export
of the contribution history is out of scope for this Epic in any case — its two verbs are to view
and to download a *receipt*.

**The affordance is a row-level column link**, supplied by STORY-002's list, and it renders on a
path that does not consult the `actions` setting: links are preprocessed per column
([`ext/search_kit/Civi/Api4/Action/SearchDisplay/AbstractRunAction.php`:898-911], the
`link`/`links` branch at
[`ext/search_kit/Civi/Api4/Action/SearchDisplay/AbstractRunAction.php`:903-908]) and formatted per
row ([`ext/search_kit/Civi/Api4/Action/SearchDisplay/AbstractRunAction.php`:575-589], the per-link
call at [`ext/search_kit/Civi/Api4/Action/SearchDisplay/AbstractRunAction.php`:584]).

**That negative claim is bounded by enumeration rather than asserted.** Within `ext/search_kit`
the setting is read at five **server-side PHP** addresses, and none of the five is on the link
path:

1. it is set to `TRUE` for a table display
   ([`ext/search_kit/Civi/Api4/Event/Subscriber/DefaultDisplaySubscriber.php`:154]);
2. it gates which bulk tasks are enabled
   ([`ext/search_kit/Civi/Api4/Event/Subscriber/SearchDisplayTasksSubscriber.php`:48-59], the read
   at [`ext/search_kit/Civi/Api4/Event/Subscriber/SearchDisplayTasksSubscriber.php`:48]);
3. it guards result-set export
   ([`ext/search_kit/Civi/Api4/Action/SearchDisplay/Download.php`:32]);
4. it guards file save ([`ext/search_kit/Civi/Api4/Action/SearchDisplay/SaveFile.php`:65]);
5. it triggers adding a primary-key field for non-DAO entities
   ([`ext/search_kit/Civi/Api4/Action/SearchDisplay/AbstractRunAction.php`:1557]).

**Those five are the server-side reads, and they are not the whole extension.** The same setting
is read on the client, in `ext/search_kit/ang`: it gates the bulk-task menu
([`ext/search_kit/ang/crmSearchDisplayTable/crmSearchDisplayTable.html`:5]) and the row-select
checkbox that feeds it
([`ext/search_kit/ang/crmSearchDisplayTable/crmSearchDisplayTableBody.html`:6], with the
select-column header class at
[`ext/search_kit/ang/crmSearchDisplayTable/crmSearchDisplayTable.html`:31]); it is one of the
conditions in `hasExtraFirstColumn()`
([`ext/search_kit/ang/crmSearchDisplay/traits/searchDisplayBaseTrait.service.js`:205]); and it is
read and rewritten by the display-admin task configuration
([`ext/search_kit/ang/crmSearchAdmin/displays/common/searchAdminTasksConfig.component.js`:20-58]).
Each of those client reads governs bulk-task or row-selection chrome, so they reinforce rather
than weaken what criterion 5 rests on: none is on the column-`link` path cited above, and with
`actions` false each either hides its control or contributes nothing — the task menu and the
row-select checkbox are conditional on the setting, the header class resolves to nothing, and the
admin component is a staff configuration screen rather than a donor surface. Two bounds on this
account, stated rather than implied: no claim is made about the setting's effect outside that
extension, and no claim is made that the server-side list and the client reads named here
together exhaust every read within it.

**A table display defaults `actions` to `TRUE`**
([`ext/search_kit/Civi/Api4/Event/Subscriber/DefaultDisplaySubscriber.php`:152-165], the assignment
at [`ext/search_kit/Civi/Api4/Event/Subscriber/DefaultDisplaySubscriber.php`:154]), so keeping it
false on the donor display is an **explicit setting**, not a state inherited by leaving the display
alone. That is what criterion 5 reviews, and it is what keeps bulk tasks and result-set export out
of a donor's reach while the row-level receipt link continues to work.

**The delivered file format is not chosen here.** It follows from two decisions STORY-003 owns —
the receipt-shape choice (`CLR-06`) and the reproduction-versus-regeneration choice (`CLR-09`) —
and the format question in its own right is `CLR-12`. Naming a format in this story would answer a
question the Epic has deliberately left open and would do so in the wrong document; every
criterion above is written to hold whichever format is chosen.

**`receipt_date` must not be written, and the prohibition STORY-003 records applies here
unchanged.** The APIv3 `Contribution.sendconfirmation` action is the obvious-looking way to obtain
receipt content, and it mutates the record: its `receipt_update` input defaults to **true** when
the caller omits it ([`api/v3/Contribution.php`:385-404], the default at
[`api/v3/Contribution.php`:397]), and the BAO mail path it calls writes `receipt_date` when the
column is empty ([`CRM/Contribute/BAO/Contribution.php`:3068-3072]). Criterion 4 depends on no
write occurring, so that action is prohibited on the download path for the same reason, and to the
same extent, as on the viewing path.

**Specification anchors.** F-004 (CiviContribute), F-013 (APIv3) and F-017 (SearchKit), together
with §6.2.2. Feature identifiers take the form `F-XXX` and requirement identifiers `F-XXX-RQ-YYY`.
These anchors point at the ingested Technical Specification, not at a file in this repository.

**Open questions.** One, owned by this story. It is classified **informational** — a defensible
default exists, so implementation may proceed while the answer is confirmed, which means *proceed
and confirm*, not *ignore*. [`epics.md`](epics.md) §7 is where that classification is
authoritative. It is not answered here, and it is reproduced in full, in the same words the closing
summary uses, so that neither document can drift from the other:

`[NEEDS CLARIFICATION: CLR-12 — In what file format is a downloaded receipt delivered, and where WeasyPrint or wkhtmltopdf is the configured PDF engine, is that external executable present at the configured path on the target instance?]`

The other open questions this story's work touches — the reuse-or-replace decision (`CLR-10`), the
receipt shape (`CLR-06`) and the reproduction question (`CLR-09`) — are **owned and raised by
STORY-003**. They are referenced above where they bear on a criterion, and deliberately not
restated as flags of this story, so that each question has exactly one owner.
